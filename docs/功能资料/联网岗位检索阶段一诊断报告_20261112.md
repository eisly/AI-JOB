# 联网岗位检索阶段一诊断报告

日期：2026-11-12  
范围：仅诊断，不修改搜索、抓取、JD 解析、Java 资格校验、排序或前端核心代码。  
基线版本：当前磁盘工作区。工作区原本已有大量未提交修改，本次未回退或覆盖。

## 1. 结论摘要

当前“岗位数量少、信息覆盖不全”的首要原因不是 Tavily 没有返回链接，也不是 Java 资格校验误杀，而是：

1. **Web 岗位提取被模型外层短超时截断。**默认真实基线中，Web 已有 159 条 Tavily 原始命中、102 个唯一 URL，但进入提取的 20 页全部因 4 个模型批次失败而产出 0 条。Web 对照运行直接记录到 5 次 20 秒外层取消；另一次真实 5 页探针在 52.953 秒时成功提取 1 条岗位，证明现有 20 秒限制会损失可提取结果。
2. **已发现页面没有可靠进入后续处理，覆盖矩阵又会提前完成。**102 个唯一 URL 只分析 20 个，剩余 82 个未分析；所有覆盖单元在 `analyzed=0、extracted=0` 时仍被标记完成，默认组合第二轮后停止。实际待处理队列保存在 `pending_pages`，停止判断却读取另一份 `web_budget.pending`。
3. **搜索覆盖仍是“轮转查询”，不是可审计的城市 × 同义词 × 求职类型计划。**Tavily/Brave 调用未实现分页，百度和腾讯只取首屏；模型生成的 alternative keyword 没有进入真实 Provider 查询。补搜轮次只重跑 Web，不补跑官网/ATS。
4. **现有漏斗指标存在重复累计和口径混淆，不能直接用于验收。**默认基线 Web 来源记录 159 条命中，总漏斗却写成 239；Web 对照来源记录 180，总漏斗写成 420。JD 理解超时后由规则降级保留 8 条，现有 `extractionSuccessRate` 却显示 100%。
5. **官网优先不是本轮 Web 未执行的原因。**本轮 Web 确实执行了；但企业官网先执行并消耗共享查询、页面和正文预算，且自身超时 15 秒，存在预算挤压。真正导致 Web 0 产出的直接环节仍是模型提取。
6. **Java 正常 null 处理基本符合预期，但边界值仍有双向误判。**实测画像学历为 null 时是 UNKNOWN；字符串 `UNKNOWN` 却被判 FAIL。技能-only 要求在其他事实未知时可判 PASS，是相反方向的误判风险。Java 资格 FAIL 在搜索处理器中只降序、不删除，因此不是本轮最大数量损失点。

**改造顺序必须是：先修模型执行与诊断口径，再修待处理队列和停止条件，然后扩展 Planner、Provider 与 ATS 覆盖。不能先靠增加搜索量或接入第二个搜索引擎掩盖 20/20 页提取失败。**

### 5.2 90 秒单批次探针

对真实查询“杭州 后端开发 实习 招聘 职位”取 5 页，保持当前模型、提示词和规则，仅把诊断探针外层上限设为 90 秒：

- Tavily HTTP 200，5 条命中、5 页可用。
- 模型用时 **52.953 秒**，输入 2449 tokens、输出 3502 tokens，最终 JSON 381 字符。
- 接受 1 条杭州实习岗位，4 页 MODEL_NO_ROW。
- 总耗时 62.359 秒。

这证明当前 20 秒限制会取消本来能够产出结果的调用。输出 token 远大于最终 JSON 所需，说明需要按任务控制思考与输出预算，而不是单纯把所有超时统一拉大。

探针岗位标题包含“字节跳动”，提取公司却为平台相关企业“成都萌想科技有限责任公司”。该样本必须进入后续人工准确性核验，说明“模型接受”不等于“招聘企业归属正确”。

## 6. 重点问题定位（按影响排序）

### P0-1：模型执行策略与外层超时冲突，造成当前最大确定性损失

**代码证据：**

- 默认思考开启且 effort 为 high：`project/agent/app/config.py:68`
- 全局最大输出 16384 tokens：`project/agent/app/config.py:78`
- Web 提取批次外层仅 20 秒：`project/agent/app/search/sources/web.py:265`
- JD 理解外层仅 15 秒：`project/agent/app/search/pipeline.py:561`
- DeepSeek 非流式请求需要等待思考和 JSON 完整返回：`project/agent/app/llm.py:107`

**实测证据：**20 页全损、Web 对照多次 CancelledError、52.953 秒探针成功。

**判断：**这是本轮最大且已确认的岗位损失环节。需要先拆分结构化提取、关键词扩展、JD 理解的模型策略，按内容长度控制批次和输出预算，并统一内外层 deadline。不能只把 20 秒全部改成 90 秒，否则会在 150 秒总预算下显著减少可处理页面数。

### P0-2：待处理页面状态断线 + 覆盖尝试次数冒充覆盖完成

**代码证据：**

- 实际剩余页面写入 `context.extra["pending_pages"]`：`web.py:205`
- 继续搜索读取 `self.web_budget["pending"]`：`pipeline.py:434`
- 最终 SEARCH_INCOMPLETE 也读取同一份未接线状态：`pipeline.py:610`
- 覆盖单元查询达到 3 次即可 completed，即使 analyzed/extracted 为 0：`expansion.py:233`

**实测证据：**102 唯一 URL 仅 20 页进入分析；四个覆盖单元均 analyzed=0、extracted=0、completed=true；默认组合两轮停止。

**判断：**82 个 URL 未处理并非“没有岗位证据”，而是没有获得分析机会。补搜应先消费未分析候选，再按真实覆盖缺口追加未执行查询；尝试次数、成功分析、岗位产出必须分开。

### P0-3：漏斗指标失真，当前无法支撑可靠新旧对比

**代码证据：**

- 多轮来源状态先合并成累计值：`pipeline.py:348`
- 随后又把累计状态加入总漏斗：`pipeline.py:393`
- JD 理解阶段把去重岗位数/降级保留数写入 extractionAttempted/Success：`pipeline.py:595`
- finalize 又把 hardFilterPass 改成最终岗位数：`pipeline.py:639`

**实测证据：**默认 Web 159 → 总漏斗 239；Web 对照 180 → 总漏斗 420；JD 理解超时仍显示 extractionSuccessRate=1.0。

**判断：**阶段二首先要保留逐轮原始指标，分别记录搜索命中、URL 去重、进入提取、模型无行、规则拒绝、硬筛、详情核验、Java 资格和截断。否则优化后也无法给出可信对比。

### P1-1：Search Planner 覆盖不完整，替代词未进入 Provider

- 初始 6 个扩展词与 3 个城市按 index 同步轮转，只生成 6 个查询，不是 18 个组合：`expansion.py:135`。
- 覆盖键只有城市和岗位类别，不把 candidateType 作为完成条件：`expansion.py:195`。
- 模型替代词只改后续 context keyword，没有证据进入真实 Provider 查询：`pipeline.py:217`、`:475`。
- 补搜只保留 Web：`pipeline.py:275`。

本轮补充查询集中在杭州，北京、上海在多次尝试 0 分析后仍被标记完成。需要可审计的多查询计划，但不应简单做笛卡尔积爆炸，应按缺口和边际新增结果分配预算。

### P1-2：Provider 和官网没有真正的分页/续查能力

- Tavily 请求只有 query、max_results 等，无页码/游标：`providers/tavily.py:27`。
- Brave 同样未传分页参数：`providers/brave.py:28`。
- 默认 30 天 freshness 不会给 Provider 加时间范围：`pipeline.py:193`。
- 腾讯固定 `pageIndex=1`：`sources/tencent.py:48`。
- 百度只取首屏并明确 PARTIAL：`sources/baidu.py:31`。
- Greenhouse/Lever 当前是全量 board 拉取后本地筛选，不能把网页分页概念机械套到这些 API。

这里诊断的是“当前代码没有分页”，不是断言 Tavily 官方一定支持某种 page 参数。阶段二实施前必须核对各 Provider 官方 API 文档；不支持原生分页的引擎应采用逻辑续查/新查询和去重，不能伪造分页参数。

### P1-3：官网优先会挤压预算，但本轮不是 Web 跳过

本轮 `needs_fallback=true`，Web 确实执行，因此不能宣称“官网导致其他数据源没有执行”。但实际存在：

- 官网/ATS 先完成后再执行 Web；
- 企业官网与 Web 共享查询、页面和 API 预算；
- 企业官网本轮 15 秒超时；
- 总预算 20 查询中 Web 记录 16，26 页面中 Web 为 20，正文总预抓 12 中 Web 为 6；
- 官网充足时 Web 可完全跳过，且没有明确 SKIPPED 原因：`pipeline.py:327`、`:331`。

应保留官网直连低噪声优势，同时给 Web 保留独立最小预算，并显式记录跳过原因和来源失败后的补检。

### P1-4：抓取、JD 结构化和来源归属仍影响信息完整性

- 当前只记录预抓发起数，不记录成功与失败原因，无法区分“未抓到正文”和“来源未提供字段”。
- 固定 5 页一批没有按正文 token 长度调度，长正文会进一步放大模型延迟。
- 详情页以结构化 JobPosting、岗位主区块和投递证据为主是正确方向，应保留。
- 探针已出现平台公司被当作招聘企业的风险，需要优先使用 `hiringOrganization`、岗位主区块和企业官网证据，平台公司信息只能作为平台属性。
- 跨来源去重已有 URL/岗位 ID/指纹/JD 相似度，不应推翻；Java 二次去重仍只按原始 URL 精确字符串。

### P1-5：Java 未知字段边界需要修，但不是本轮数量瓶颈

| 场景 | 实测/静态结果 | 判断 |
| --- | --- | --- |
| 画像学历 null，岗位要求本科 | UNKNOWN | 正确 |
| 画像学历字符串 UNKNOWN，岗位要求本科 | FAIL | 应改为无法解析的 UNKNOWN，不能当作明确冲突 |
| 岗位要求学历为非法值 | UNKNOWN | 当前已有保护 |
| 毕业年份/经验事实为数字字符串或非法文本 | 可能类型转换异常 | 应统一归一化为 UNKNOWN，而不是异常或 FAIL |
| 只有技能列表，其余要求与事实未知 | PASS | 存在误判通过风险，与“完全无硬要求时 UNKNOWN”的保护不一致 |
| 城市/求职类型缺失 | 保留并警告 | 不会因未知被前置淘汰 |
| 公司规模未知且 includeUnknownSize=true | 保留 | 本轮配置不会淘汰 |
| 资格 FAIL | 仍持久化，仅排序靠后、分数清空 | 不是本轮数量减少原因 |

Java 还丢弃 Python 根对象中的 `metrics/dedupe`，自己的 droppedCount 不区分城市、类型、规模和无效字段，uniqueCount 在截断后赋值。上述是可观测性和口径问题，应在阶段二补齐。

## 8. 阶段二具体改造方案（按影响与依赖排序）

### 第一步：先修诊断口径，不改变召回规则

涉及：

- `search/pipeline.py`
- `search/sources/web.py`
- `search/metrics.py`
- `search/budget.py`
- Java `JobSearchResultHandler.java`

内容：

1. 每轮保存不可变来源快照，总漏斗只累加当轮增量，禁止累计状态再次累加。
2. 明确 `stopReason`：目标达成、覆盖完成、无新增、轮数、API、时间、Provider 失败、无待处理页面等。
3. 分开记录模型未提取、模型调用失败、规则拒绝、城市/类型/规模拒绝、详情抓取失败、Java 资格与截断。
4. 抓取记录 attempted/succeeded/failedByReason/bodyChars/renderUsed；JD 模型理解与规则降级分开计数。
5. Java 保存上游 metrics/dedupe，并补资格 PASS/UNKNOWN/FAIL、截断数和逐项拒绝原因。

验收：同一运行满足数量守恒；159 不得再被汇总成 239，模型降级不得显示成模型成功。

### 第二步：修模型执行策略，立即用相同画像复跑

涉及：

- `app/llm.py`
- `app/config.py`
- `search/sources/web.py`
- `search/pipeline.py`
- 现有 `app/skills/prompts/job_search_extract.md`

内容：

1. 不更换 DeepSeek，不破坏 reasoning_content → Java → 前端展示链路。
2. 按调用类型设置思考强度、最大输出和 deadline：关键词扩展与结构化提取使用短输出/较低思考；JD 理解保留所需思考能力和展示。
3. Web 批次从固定 5 页改成按估算 token/正文长度组批，长页单页处理；保留原文引文和真实性校验。
4. 对齐内层 HTTP read timeout、外层 wait_for 和全任务 deadline，避免内层仍在生成而外层 20 秒取消。
5. 记录成功/取消/格式失败、输入输出 token 和单位岗位成本；取消不盲目重试同一请求。

验收：使用本次完全相同的画像和预算复跑。只有出现新的真实相关岗位才算改善；仅模型成功率提高但岗位仍为 0，不算完成。

### 第三步：修待处理页面与提前终止

涉及：

- `search/pipeline.py`
- `search/sources/web.py`
- `search/expansion.py`
- `search/budget.py`

内容：

1. 将 pending pages 纳入共享 SearchState，停止与警告读取同一份队列。
2. 有未分析候选时优先消费候选，再发新查询；同查询不重复发送。
3. 覆盖单元拆分为城市 × 岗位族 × 求职类型，记录 planned/executed/analyzed/extracted/exhausted。
4. “查询达到次数”只能标为尝试耗尽，不能伪装成已覆盖；0 分析且仍有候选/新查询时不得提前停止。
5. 保留 API、页面、轮数和总时长硬上限，耗尽时明确 `BUDGET_EXHAUSTED`。

验收：默认基线中 82 个未处理 URL 必须进入队列统计；不能再出现 analyzed=0 却 completed=true 且无停止原因的结果。

### 第四步：在前三步有效后扩展 Search Planner 与 Provider

内容：

1. 抽取独立 Search Planner，复用现有关键词族，增加岗位名称同义词、城市、求职类型补检和查询优先级。
2. 多查询并发按 Provider 限流；按新增唯一 URL、有效岗位和覆盖缺口分配预算，而不是机械跑满笛卡尔积。
3. 统一 `SearchRequest/SearchResult` 的 query、limit、cursor/page、freshness、capabilities、attempts、cost、duration。
4. 按官方文档实现 Provider 原生分页；不支持分页的 Tavily 使用逻辑续查与查询去重，不伪造 API 能力。
5. Brave 继续作为可配置备用/并行 Provider；未配置时正常降级。它不是修复当前模型 0 提取的前置条件。
6. 给通用 Web 设独立最小预算，官网充足跳过 Web 时记录 `SKIPPED_OFFICIAL_SUFFICIENT`，官网失败不能被充足条件掩盖。

### 第五步：复用并扩展官网/ATS，再完善抓取、去重与可信度

1. 百度、腾讯在官方接口支持且预算允许时翻页，记录 total/pagesFetched/pageExhausted；不能继续只取首屏。
2. 复用 Greenhouse/Lever 适配器，按公开合法 board 配置扩展企业；不为数量硬编码无关企业，不绕过登录、验证码或风控。
3. Greenhouse/Lever 全量接口保持原语义，按 updated_at/岗位 ID 做增量和状态同步，不重复制造分页请求。
4. 抓取兜底顺序为 Tavily 正文 → 静态详情 → 可用的渲染能力 → 低证据摘要；每步记录原因，访问失败不判 CLOSED。
5. JD 优先结构化 JobPosting 和岗位主区块，模型只处理岗位正文；薪资、规模、经验、学历、城市保留原文和 fieldSources。
6. 修正招聘企业与平台运营方归属；平台公司信息不得覆盖 hiringOrganization。
7. 保留 Python 多维去重，Java 使用上游 fingerprint/aliases 做第二道防线；不同岗位 ID 的同标题岗位不能在无证据时强行合并。
8. 来源可信度用于排序和解释，不把官网设为绝对优先，也不让 UNKNOWN 等同 CLOSED。

### 第六步：修 Java 未知字段边界，保持现有推荐流程

1. 非枚举画像学历、非法数字事实统一归一化为 UNKNOWN；只有明确且可比较的值冲突才 FAIL。
2. 区分“岗位未设该要求”和“要求存在但无法解析”；统一技能-only 与无硬要求的整体资格语义，避免未知被误判 PASS。
3. 保留 FAIL 不删除、UNKNOWN 可入候选的当前搜索语义，除非另有明确产品规则，不借修复增加新的淘汰。
4. 不改变 DeepSeek JD 理解输出契约、Java 匹配评分接口和前端展示字段；新增指标保持向后兼容。

## 9. 阶段三验证设计

### 9.1 同条件新旧对比

固定本次画像、关键词、城市、类型、来源和预算，保存优化前 JSON 作为基线。每一步核心修复后单独复跑，最后再跑完整组合，避免把多个改动的影响混在一起。

必须输出：

- 原始召回数（按来源、Provider、查询，未去重）
- 唯一 URL、唯一岗位数及去重方法
- 进入抓取数、抓取成功数、403/404/超时/渲染失败数
- 进入提取数、模型无行、模型失败、规则拒绝、JD 解析成功数
- 城市/类型/规模淘汰数及原因
- 四态核验分布
- Java 资格 PASS/UNKNOWN/FAIL、截断数
- 最终有效岗位数、来源和城市覆盖、陈旧率
- API 逻辑请求/真实 HTTP 次数、token、总耗时和单位有效岗位成本

至少增加一组不同岗位族画像，防止只针对“后端开发”过拟合。相同 60 次/150 秒预算用于主对照；如需提高预算，必须另列一组，不得与主对照混算提升。

### 9.2 人工核实样本

从新旧结果并集分层抽样，覆盖每个城市、来源、UNKNOWN/CLOSED、新旧新增岗位和同标题不同 URL 岗位。样本字段至少包含：

- 是否真实岗位详情页
- 是否匹配岗位方向、城市和求职类型
- 招聘企业是否正确，是否误用平台运营方
- 是否重复
- 是否仍在招及证据
- 发布时间/更新时间与新鲜度
- 薪资、规模、经验、学历是否来自原文

将本次探针中“标题为字节跳动、提取公司为成都萌想科技”的样本列为必查项。

没有形成人工标注的相关岗位全集前，Recall@K、Precision@10、NDCG 继续标为 `NOT_MEASURED`；只能报告样本准确率/样本召回，不虚构全局召回率。

### 9.3 通过标准

- 主要改善依据是**新增真实、相关、字段可追溯的岗位**，不是 URL 或模型调用增加。
- 若仍只有官网结果，必须指出具体阻塞阶段和证据。
- 不以降低 JD 引文、城市、求职类型、企业归属和在招证据标准换取数量。
- 保留现有 DeepSeek JD 理解、Java 匹配评分、前端展示和岗位推荐回归测试。
